## What landed

The collector writes each project's five `projectTabs` records and its status record into the local SQLite database, by the same rules as `export_board.py` and `refresh.py`. Tab assembly moved into the shared `exporters/derive.py`, so the board and the local app derive identical documents from one implementation; `derive.git_default` was added and `git_doc` now applies the empty-branch rule itself, so no derivation is duplicated in the caller.

**This completes the local-first path.** Collector → SQLite → server → page, with every document the published board shows now derivable locally. The one deliberate gap is `pulls`: listing pull requests needs `gh`, which contacts GitHub, and the collector is designed never to touch a network host — so the local GitHub tab carries no pull requests (spec Q-2).

## Three things worth carrying forward

**The gate caught a data-loss bug before any code existed.** `projectTabs` has two writers — `export_board` owns the five tabs, `export_sessions` owns `findings` (PBI-011) — and neither may touch the other's. Round 1's F-2 found that deriving the local owned-tabs set from `records.TAB_NAMES` would put the findings record outside the *intended* set; deletion is *stored minus intended*; so the collector would have deleted the findings ledger on **every 60-second pass**, destroying exactly what PBI-011 publishes. The set now comes from a local `tabs.OWNED` constant, and reverting `tabs.owns` to `records.TAB_NAMES` still fails both `ForeignSuffixes` cases. Anyone adding a tab name should check for this pattern elsewhere.

**The build was right and the approved spec was wrong.** `tabs.carry` deviated from §4.4 row 4's "Store nothing" for an already-carried record. Returning nothing drops it from the intended set, so §6.2 deletes it on the **third** pass — losing the carry the rule exists to preserve. The code reviewer reproduced that from the literal wording and adjudicated the deviation correct; the spec is amended to revision 4 to match the code. A spec that has passed two gate rounds can still be wrong, and it took a build deviating plus a reviewer asking *which* was at fault to find it.

**The same bug class appeared twice, on paths nobody connected.** The spec gate's N-4 caught that `UnicodeDecodeError` subclasses `ValueError`, so a confined per-project failure and the `load_data` whole-pass carve-out cannot share one block-level handler. Code review round 1 then found the identical hole in `GIT_ERRORS`, which omitted it — one project's non-UTF-8 git output (an unlimited `git log %s`, or a branch name) escaped the confined region and failed **every pass indefinitely, writing nothing**, taking healthy projects down with it. Fixed test-first, with the error raised from git's own output rather than a synthetic exception. Round 2 swept further: twelve pathological shapes all degrade inside `READ_ERRORS`, and the one residual (`derive.git_doc`'s pipe unpack) was probed and found unreachable.
